# L0: user request → Task specs → verified outcome

This is the operating specification for the **existing** Teams Orchestrator tools, not a second planner, task store or controller. L0 is the current parent model. The extension supplies mechanical dispatch/ownership/acceptance; it does not interpret requirements or choose outcomes. Native read/write tools are sufficient to author Task specs. No prepared solution patch, mandatory file named SPEC.md, fixed task count or fixed role chain is required.

## 1. Interpret and choose

- Start with the user's actual request and applicable project instructions. Read relevant source and existing acceptance criteria. Identify observable outcomes, non-goals, authorized actions, unresolved material decisions, and the real verification entrypoint. Ask only for missing information that materially changes correctness, scope or authority; do not invent requirements to simplify testing.
- Use direct work for small bounded tasks unless delegation has a concrete context, isolation, duration or independent-judgment benefit. Ordinary requests do not create persistent Goals. Task Pi requires an explicitly authorized Goal; otherwise use the already available ordinary team handoff or direct path, within the original mandate. Missing Task Pi capability before dispatch is not permission to install capabilities. A failed/unknown dispatch is not permission to switch execution modes.
- Derive task count and boundaries from outcomes, not roles or test categories. One task can need several roles. Two acceptance criteria for the same deliverable generally belong to one task, not two workers redoing that deliverable. Split only when each task has a meaningful deliverable and a reason to own a separate context.
- Preserve exact interface literals (selectors, keys, routes, file formats), behavior and scope through Task criteria/context and Worker→leaf handoff; a summary such as “empty state” must not erase a required selector. Check original requirements → task evidence coverage before dispatch and again against the candidate. This is L0 judgment, not a runtime keyword gate.
- Record requirements → tasks → checks and dependency reasoning briefly in the existing Goal/task description or normal handoff. Do not create another registry or require an additional approval ceremony for routine decisions already authorized. User-specified order is binding. Parallel tasks must not need each other's unproduced output and must not compete for shared writes or external resources. Worktrees isolate files, not databases, ports or production effects.

## 2. Author the actual Task specs

Read the focused Goal/task state through the public Goal tools; resume does not mean redispatch. Create/update task definitions through those tools, observe any native confirmation, then use returned goal/task IDs. L0 versions its Task spec with a positive taskRevision (1 for the first spec); do not assume Goal-X returns a Task-runtime revision. A team-backed task remains completion-blocked until its own receipt/readback. Do not copy IDs from examples or prior runs. Do not mutate Goal files with shell/write.

L0 writes a bounded JSON spec **inside the current workspace**, using the native write tool, before calling `team_task_dispatch`. Prefer a project-approved, already ignored control location (for a normal Git clone, its real `.git` directory is suitable; linked worktrees have a `.git` file and need a separately approved in-workspace location). Do not widen ignore rules/write scope or overwrite unrelated specs just to pass clean-source checks. Dispatch will seal a contract: change a draft before dispatch; after a reservation exists, use the original execution and reconciliation rules, not edits to reopen it. For a closed, proven failed staged check, the original live L0 may author a new `taskRevision` spec and use `team_task_revise`. For a fully captured BLOCKED product review on an opted-in Task, use `origin:"blocked-review"` with `additional_checks` (or `[]`) and omit `spec_path`: the host mechanically inherits the sealed contract and increments taskRevision. L0 diagnoses the defect and chooses any necessary trusted regression; it does not regenerate immutable fields. A host-proven isolated merge conflict has the analogous `origin:"integration-conflict"` form described below. These paths stay within unchanged scope and existing repair/budget limits, create a **new** execution and never edit the old sealed one.

The spec uses the current `teams-task-runtime/3` fields below. `task-runtime/contracts.mjs` is the authoritative validator; `TaskOrchestrator.prepare` creates runtime identity. **Do not add a new wrapper schema or another spec compiler.**

| Field | Source and meaning |
| --- | --- |
| `schemaVersion` | `teams-task-runtime/3` for new work. |
| `goalId`, `taskId`, `taskRevision` | Actual public Goal/task identity, not `pending`; L0's spec revision starts at 1. Runtime creates project/execution/owner identity; do not author an `identity` object. |
| `objective` | This task's observable outcome and necessary constraints, not the entire L0 transcript or Goal orchestration instructions. Specify behavior to implement/diagnose; do not require an approved patch unless the user actually supplied one. |
| `nonGoals` | Array of bounded exclusions from the user's mandate. |
| `workspace` | Exactly `sourceRoot`, `worktreePath`, `baseCommit`, `sourcePaths`, `allowedWritePaths`. Canonical actual source root; actual Git base; `worktreePath:null` for managed role worktrees; relative paths for scope and writes. `sourcePaths` are source-evidence roots, **not** a claim that isolated writer outputs already exist in the original checkout: a planned new file/directory may be absent at the clean base, and the host records its absence in the source manifest. Keep actual product writes inside `allowedWritePaths`; do not pre-create fake product files or copy the worktree patch into the target just to make a source path exist. Distinguish directories from readable files. Do not claim a dirty/unknown baseline is clean. |
| `criteria` | Array of `{id,text,requiredEvidenceKinds}`. Stable task-local IDs and observable behavior, covering the assigned original requirements. Current acceptance supports `host-check`; an unsupported required kind remains a gap, not permission to silently substitute a weaker requirement. |
| `checks` | Array of `{commandId,executable,argv,cwd,timeoutMs,expectedExitCode,criterionIds}`. Use existing trusted checks when they prove the behavior. Executable is canonical absolute; argv is an array, cwd equals sourceRoot, expectedExitCode is 0. Every assigned required behavior needs appropriate evidence. A version check is not feature verification; exact fixture equality is not general product correctness. |
| `policy` | Exactly `risk`, `allowedRoles`, `maxActiveRoleRuns`, `maxRoleSpawnsPerTask`, `maxProductRepairsPerRole`, `maxReportRepairs`, `maxProcessRestarts`, `maxTaskTokens`, `deadlineMs`, `integrationMode`, `review`, with optional `workerAllowedRoles`, `tokenBudgetMode` and `reviewProductRevision:"within-scope-once"` (only when the original authorization includes this one-round product repair). New v3 dispatch seals `tokenBudgetMode:"shared"` by default; `member-hard` exists only for explicit legacy compatibility. Derive values from current authorized settings/budget and task risk, not old E2E allocations. Do not silently enlarge limits. |
| `policy.workerAllowedRoles` | Optional nonempty, unique subset of the total Task `policy.allowedRoles`, for v3 only. Restricts Worker single/wave/replacement dispatch; omitting it preserves the old Worker ceiling. It never narrows or grants L0 final-review authority (`policy.review`) and never changes native role profiles. When review belongs only to L0, keep its role in the total Task/review ceilings but omit it from this Worker subset. Like the rest of policy, the subset is immutable across repair/revision. |
| `policy.review` | `{authority:"l0-source-bound",allowedRoles,allowedTools}`. Before sealing a Task, inspect the selected reviewer role's current tool profile and account for **every** effective read-only tool ID it exposes, including resolved MCP names and internal structured output. For example, `team.reviewer` may expose `grep`, `find`, `ls`, lens readers and code-graph tools in addition to `read`; `["read","structured_output"]` alone is not a compatible ceiling for that profile. Review roles must also be in policy.allowedRoles. v3 requires the existing source-bound review path; do not bypass it because the task seems easy. |
| `contextRefs` | Array of `{uri,sha256}` for relevant existing files, relative to sourceRoot, with hashes calculated from actual bytes. Include the real requirements/context file when useful, whatever its filename; no mandatory product SPEC.md. Worker receives these refs and scope from the sealed contract. Never include credentials. |

For a fresh product under `app/`, `sourcePaths:["app"]` and `allowedWritePaths:["app"]` are valid even if `app/` does not yet exist in the original checkout. The source snapshot binds an explicit `kind:"absent"` entry until staging; only the managed native patch, host checks, fresh source-bound review and AcceptanceReceipt can establish the new product. An absent path is not permission to follow symlinks, include credential paths or accept target drift. A genuine source-read failure is reported to the owner for cancel/reconciliation, not repeatedly submitted as a new Task result.

Do not call the sealed-contract validator with invented identity fields to validate a draft. The public dispatch owns that conversion. Its preparation diagnostics expose current evidence/check-mapping and relocation limitations; they are not semantic approval, a new gate, or permission to edit a sealed contract. Resolve known capability gaps while authoring the draft, not by substituting weaker evidence after dispatch.

For staged checks, use integration-local relative argv (for example `.` for the relocated cwd), not an argv string containing the original sourceRoot. Runtime will not rewrite shell text. `policy.review.allowedTools` contains resolved tool IDs, not profile `mcp:server/tool` selectors. **Do the role-profile inventory before dispatch:** dispatch now checks the public effective inventory (including internal structured output) before Task reservation; a proven missing tool is a correctable draft-spec rejection, not an invitation to widen a sealed ceiling. The source-bound review preflight after stage remains the final authoritative check for exact launch/profile drift. Never copy an example tool list; if no compatible read-only inventory fits authorized policy, stop before sealing.

The rendered Worker procedure prompt must fit 6 KiB of UTF-8 bytes. Product requirements stay in the complete sealed `task-request.json`, not duplicated in that prompt. Worker must read it before assigning roles and carry exact applicable requirements, interface literals, scope and contextRefs into leaf handoffs. Preparation validates both the E0 prompt and the required E1 repair prompt for an opted-in product revision before allocating an execution/reservation. Large requirement text does not need to be shortened after sealing; a genuine remaining prompt-cap rejection is correctable only before allocation, with no dropped requirements or reopened execution.

Validate semantic consistency **before** dispatch: task objectives collectively satisfy the original request; checks measure those objectives; dependencies/allowed writes reflect actual work; authority and resources are available. A syntactically valid but irrelevant duplicate task is still a planning error. Do not weaken criteria or change the user's request to make a candidate pass.

For `approved-integration`, check the **pre-apply source-bound review** phase when writing criteria and its review assignment. Every criterion the reviewer must mark met must be decidable from the frozen candidate, requirements and designated staged-check evidence available *then*. Do not make post-review apply/confirmation evidence—an immutable target plan, the user's per-plan decision, target apply/readback, final host checks or AcceptanceReceipt—a prerequisite for that review's PASS: the plan cannot exist until the review is sealed. Keep those later requirements in the Goal/task verification contract and L0's mandatory acceptance sequence instead; this does not waive them or authorize the reviewer to treat pending evidence as present. For example, review candidate behavior against its staged check receipt now; require the exact target plan, confirmation and applied-target behavior only at their later gates.

Checks may need new regression code. Arrange trusted host execution and appropriate scope before dispatch; do not give a reviewer write/shell authority to invent acceptance after the fact. The runtime's schema/source/usage checks do not prove semantic coverage.

### Role effects, isolation and host checks

Choose role effects and isolation separately **before sealing the Task**. An expected empty diff does not make a write-capable mode read-only. The existing `team_role_spawn` contract is:

| Role mode | Write authority | v3 single-form isolation |
| --- | --- | --- |
| `mutation`, `check` | Write-capable; requires nonempty `allowedWritePaths`, even if no change is expected. | Managed `worktree`; explicit shared writes/checks are rejected. |
| `read-only`, `review` | No source changes, even when the Task has allowed write paths. | `shared`; does not produce an isolated candidate handoff. |

For unchanged-source validation with `allowedWritePaths:[]`, bind the actual current source/base and use the existing wave form `{key,reason,runs}` with a permitted role, `mode:"read-only"` and `isolation:"worktree"` when a native candidate handoff is required. A wave may contain **one run** solely to express isolation; it does not require parallel work or another Task. Preserve the native empty-patch handoff. Shared reader reports cannot replace it. Managed worktrees are not security sandboxes.

`check` is not a synonym for inspection or for the controller-authored `checks` in the Task spec. L0's existing stage/check seam runs those designated checks; leaves report untested host-check criteria as `indeterminate`. A zero-diff candidate still needs native terminal/usage evidence, staged host checks, fresh source-bound review and AcceptanceReceipt; it does not inherit acceptance from earlier component receipts or a previous manual check.

A rejection does not authorize switching mode/isolation, expanding write scope or weakening a sealed requirement. Correct only an input that remains within existing authority; if the sealed assignment is incompatible, report the blocker and follow reconciliation/owner-decision rules. This guidance explains existing gates and defaults; it adds no automatic selector, fallback or retry.

## 3. Budget and execution

- Keep the original authorized cumulative ceiling and counting window. Account for earlier successful/failed/cancelled work, current L0 and all Worker/leaf/review usage including cache. Missing history is unknown, not zero. Assign task ceilings within the remaining authorized allocation and leave room for coordination/review; a Task ceiling is not a leaf allocation.
- Within a new Task, Worker, roles and final review share one pool. Role `max_tokens` / review `maxTokens` is an initial cumulative input/output/cache estimate and reservation, not a per-response output limit or a separate hard quota. Request headroom may grow automatically from unreserved Task funds, never from another active member's holds or by raising `maxTaskTokens`. Settled actual usage replaces consumed holds; unused holds return when the member finishes. Do not micromanage or inflate role estimates to bypass a failure.
- The existing ledger atomically reserves headroom before a Worker/leaf/review model request. Text headroom uses conservative serialized-context bytes plus the model's maximum output; media/unavailable context uses the model window. Compaction retains headroom for native summarization. This may conservatively deny a request; it is reported-usage admission, not a tokenizer, a provider billing firewall, or a new retry policy. Unknown counters/termination retain reservations and require reconciliation. Old sealed contracts keep their original semantics; no retroactive top-up of cancelled work.
- Before a wave, sum all planned Task ceilings plus already committed/active allocations against that remaining amount. Reservations are not actual usage: replace closed allocations with actual usage once, never add both or count a session twice. If complete accounting or the approved budget is unavailable, do not guess an amount or start a wave.
- The original live owner exposes `closedUsage` at cancel/reconcile/drain. `status:unknown` is not zero, even when cleanup succeeded. For closed historical executions, use the read-only native inventory reader rather than selecting intermediate role-usage snapshots; never impersonate the old controller or overwrite its evidence. L0 still supplies campaign membership and the parent/L0 history. The Task runtime enforces per-task usage; the E2E observer has its own cumulative budget checks. **Neither is currently a universal cross-project campaign ledger or global hard token cap.** Do not claim otherwise or reset a campaign for a new request.
- Call `team_task_dispatch` with `spec_path` (absolute), `benefit` and `benefit_detail` using its current public schema. When the user has authorized or required the Goal→Task path, raw `subagent`/`run` implementation or review cannot replace it; a missing execution ID is a dispatch blocker, not authority to switch modes. General native subagent `acceptance:false` remains valid; only a selected report acceptance configuration may require `outputSchema`. Neither option waives the Task's required checks, independent source-bound review or AcceptanceReceipt. Independent tasks may be dispatched after the previous call returns RUNNING, before collecting either. Do not force parallelism or task count. Dependent work waits for verified prerequisite output; re-read source/base before authoring its spec.
- `maxRoleSpawnsPerTask` covers both Worker role launches and L0 source-bound review launches. Plan for the complete outcome within the approved ceiling; plan-review allocation diagnostics are a snapshot, not a reservation. Start-review rechecks current usage/lifecycle/limits. Internal Worker review is optional task-local work only when its role is inside the Worker ceiling, not a replacement for final source-bound review; avoid repeating it without a distinct purpose. A Worker-only role denial occurs before native launch/role allocation and preserves the active Task: continue permitted work or return `ready_for_acceptance` with pending host gates indeterminate when only L0 gates remain. Do not seal BLOCKED merely because L0 must perform the final review.
- Worker owns task-local role selection and candidate preparation. L0 handles cross-task dependencies, integration and acceptance; do not micromanage/repeat role work or manually materialize a patch into an ad-hoc browser worktree. The declared stage/check seam owns candidate relocation and host evidence. Use `team_task_collect` with bounded `wait_ms`, not shell polling. `collection:waiting` only ends this wait window: continue the same execution when needed, not a new dispatch. Task deadline and unknown process state remain stop/reconciliation conditions. Ready is a candidate, not delivery.

### Task-local branch recovery

Task Pi uses the existing `team_role_control`, not another controller:

- `action:"status"` reads its owned inventory once. `action:"stop"` with `run_id`, member `key`, and causal `reason` targets only that native child. A stop reply is not terminal proof; the recorded request is one-shot, including unknown transport outcomes. Healthy siblings continue; wait for native completion rather than polling.
- After the current wave has proven termination and measured usage, `action:"repair"` additionally takes `task` (bounded repair instructions) and `max_tokens`. It creates one fresh same-role/mode/isolation replacement in the **same execution**. Writers/checks remain in managed worktrees; shared read-only/review branches may be replaced only against the clean original target. Worktrees/read-only prompts are not security sandboxes: diagnose effects, never assume an interrupted shell was harmless.
- Diagnose the causal defect and the intended recovered behavior first. Preserve successful siblings and failed attempts. The replacement must read the SHA-bound original assignment and previous evidence, then return its **complete corrected contribution**, not reimplement siblings. Read-only replacements must not write source. A report-format problem does not authorize implementation/check replay; native `acceptance.childReportParseError` is rejected at repair admission. Native process success is not product correctness: a settled complete child with a diagnosed product defect remains eligible, while all unselected siblings remain unchanged.
- `maxProductRepairsPerRole` bounds each branch's replacement lineage; every attempt also consumes the original Task's spawn, cumulative usage and absolute deadline limits. Native no-start facts permit diagnosis, not automatic relaunch. Missing exit/terminal/usage evidence, signal/timeout, interrupted/stopped or turn/tool-budget termination (even with exit code 0), source/owner drift and exhausted resources remain blockers for that branch; none may be renamed success or discarded.
- `teams-role-repair/1` progress binds predecessor status and full assignment byte digests, successor identity/task digest and repair ordinal. All original run IDs stay in the result inventory and accounting. Integration selects successful unreplaced contributions plus validated replacements; it can retain a successful sibling from a failed root only with complete native result/terminal evidence. Unreplaced failures and incomplete captures still block acceptance.
- Fresh merged checks, source-bound independent review of the recovery lineage, and normal acceptance/Goal readback remain mandatory. This is pre-result Task-local recovery, not permission to reopen a sealed result or reset the one-successor `team_task_revise` allowance.

L0 distinguishes a locally blocked Task from a blocked Goal. Diagnose dependency impact, continue independent authorized Tasks, and drain only affected executions when necessary. A collected blocked/failed result is not stageable or acceptable; it is not by itself a reason to cancel healthy Tasks or pause all coordination. Escalate a concrete missing decision/authority/evidence when existing recovery cannot finish the outcome. Only genuinely unavailable remaining progress or an explicit user stop blocks the whole Goal.

### Review-only product candidates

For v3 with required L0 source-bound review, a complete, terminal native candidate with a disclosed product defect may use `outcome:"ready_for_review"`. Keep the corresponding criteria `not_met`; do not disguise known failure as pending-host `indeterminate`. This is distinct from `blocked` (missing authority/artifacts, unresolved effects or an out-of-scope decision), and does not make those old results stageable. The existing workspace, native handoff, usage, owner and deadline checks still apply.

`ready_for_review` permits isolated stage (including its declared checks), prepare/plan/start/collect/seal of source-bound review only. Final `run_checks`, target planning/apply and acceptance require `ready_for_acceptance`; even a PASS review cannot override a review-only result or its `not_met`. Ordinary untested host gates alone still use `ready_for_acceptance` with `indeterminate`. Do not reopen or rewrite any sealed result.

For a genuine captured BLOCKED product review, the existing opted-in `origin:"blocked-review"` path may admit the sole successor from either reviewable outcome. Worker observations alone do not authorize revision. Every old artifact, immutable requirement/policy, closed usage and original deadline remains bound; E1 must actually correct the defect and obtain its own passing checks/review and acceptance-ready result. Failed-check, report-only and conflict eligibility are not expanded by this outcome.

## 4. Accept the user's outcome, not just the tasks

For each candidate follow the existing stage → designated host checks → source-bound review → acceptance tools. Stage already executes its declared relocatable checks; `team_task_run_checks` verifies unchanged stored receipts. Do not manually rerun them against the original target or interpret `acceptance:not-assessed` as absent checks. Use their returned exact IDs, keys, digests and file paths; do not guess report paths or read a directory as a file. Independent review must inspect the actual candidate and whether its evidence supports the assigned requirements.

- `verify-only` delivers a verified patch and leaves the original target unchanged. It does not satisfy a request for an installed/running change unless that delivery mode was agreed.
- `approved-integration` follows staged candidate/checks → independent source-bound review PASS and seal → immutable exact target plan and inspection → separate per-plan user confirmation → approved apply and applied-source review → post-apply host checks and AcceptanceReceipt. The reviewer evaluates only evidence available before the plan; later gates remain mandatory. A plan or spec is not deployment/apply approval. No commit/push/deployment without explicit authority.
- Separate accepted patches do not prove the combined system works. When the request needs a combined deliverable, plan its actual integration and final entrypoint verification; serial apply may invalidate other tasks' source snapshots. Do not complete the overall Goal based solely on the number of receipts.
- Complete each task only with its own fresh AcceptanceReceipt and matching public readback. Completion hooks resolve the native session's `pi-goal-focus` identity and the latest Task execution, including closed failures—not just open reservations. Missing native focus blocks completion rather than guessing another Goal. Batch updates may combine genuinely ready tasks; never borrow a sibling's receipt. Before Goal completion compare the final deliverable against **all original requirements**, verify no unresolved executions/reservations remain, and record audit skip as skip.
- Keep bounded durable evidence references in normal results/Goal records. The same L0 may own the whole flow; an extra supervising parent is not required. Do not make an audit-copy/README workflow a prerequisite to valid acceptance. Archive only what is needed, from exact tool references, without re-running successful work.

## 5. Errors and changed requirements

Public schema rejections and host-bound `teams-input-rejection/1` results identify requests rejected before the requested launch, and may be corrected in the native loop within existing authority. Bind the tool/call/input and phase; preparation metadata may already exist, so do not call this zero side effects. Review tool mismatch reports approved/effective/excess tools; it does not authorize changing a sealed policy. If no compatible option exists within the approved ceiling, return the capability blocker. Unclassified Task errors, unknown side effects, stale source, failed safety/usage/deadline gates or missing terminal proof require exact execution reconciliation/owner-safe drain; never infer a new launch is safe. General tool errors remain evidence for L0 to reconcile, not a permanent observer failure latch or automatic replay permission. A native L0 Bash timeout is a runtime stop condition: the observer preserves its error and invokes the existing owner drain; do not continue or retry because the command was intended to be read-only. A timeout phrase printed by a program, or a normal generated-syntax/nonzero-exit error, is not that native timeout receipt. Native configured bounded provider retries are not Task redispatch. Pause/Goal completion does not itself stop Workers. Preserve terminal results and reported failures.

For an explicit `execution_id`/`previous_execution_id` not in the live controller's dispatch inventory and not in the ledger, the public tool performs a read-only lookup before entering the operation and returns a bound `execution-selector` rejection with `preparationEffects:"none"`. A known dispatched ID remains an operation/state failure if its row disappears; it is never reclassified as a typo. Re-read the exact ID from the existing public result and correct only that selector in the same authorized flow; there is no fuzzy matching, new execution, replay or ownership bypass. Healthy Tasks remain live. Internal missing-row assertions, a row disappearing after successful lookup, database/I/O failures and all existing owner/source/deadline gates remain hard failures, not input corrections.

A host-bound completed-check-failure result means the command exited nonzero with intact source/owner evidence, not that runtime has diagnosed a product bug. Keep the same L0 available to inspect its exact receipt/log and distinguish checker assumptions from candidate defects. If repair is authorized, cancel/drain the failed execution and admit its bounded same-Task successor; pause the Goal only when diagnosis, evidence or authority prevents progress. A failure blocks acceptance, not all L0 diagnosis. Failed integration still blocks review/acceptance and reuse; no sealed edits or check replay. Signal/timeout/spawn errors, changed source/owner, or missing evidence remain runtime/unknown stop conditions. A new Goal/workspace is not a repair strategy or a budget reset. For a closed v3 shared Task with `ready_for_acceptance` result and a completed nonzero *stage host-check* (intact source/effect evidence), after diagnosis the original live L0 can use `team_task_revise` with an incremented same-scope spec, exact old result digest and failed-check receipt ref/SHA. This is at most one new candidate execution under the original Task ceiling, with prior actual usage carried forward; do not use it to replay the old check. Ordinary dispatch cannot bypass a preserved staged integration failure or top up/change the scope of a bounded v3 process restart. New **candidate repair** must repeat its own stage/check, independent final review and acceptance. For a different, closed v3 shared **verify-only** Task with one fully captured independent BLOCKED review wave containing an explicit blocker finding and verified successful original writer/staged checks, the same live L0 may instead call `team_task_revise_report` with a `taskRevision+1` same-scope spec, exact previous result digest, and the old `integration/reviews/<key>/complete.json` absolute ref/SHA. The new Worker corrects the report only: native role dispatch is forbidden; host replays the identical original patch in an isolated clone, verifies original writer/check receipts without rerunning checks, and requires a **new** source-bound independent review resolving every prior finding before AcceptanceReceipt/3. Prior actual usage, owner epoch and original Task ceiling carry forward; old BLOCKED evidence remains unchanged. For a closed BLOCKED **product** review, `team_task_revise` with `origin:"blocked-review"` is available only if the original sealed v3 shared Task had `policy.reviewProductRevision:"within-scope-once"`. `collect-review` returning `verdict:"blocked"` is **not** a candidate to `seal-review` (PASS-only). The model-visible collect handoff supplies the sealed `resultRef`/`resultDigest`; the bound review handoff supplies `resultDigest`, `completionRef` and `completionSha256`, plus compact finding counts. Read **all** reports/findings from that SHA-bound completion before diagnosing; counts are not the full review or revision authority. Save these exact selectors before cancel/drain: after closure, read the saved files directly, never call collect/stage/review on the closed execution. Map them to `expected_previous_result_digest`, `review_failure_ref` and `review_failure_sha256` below. Preserve the captured completion, diagnose the genuine in-scope source defect, cancel/drain E0, then request the same Goal/Task revision+1. The public call uses `previous_execution_id`, `expected_previous_result_digest`, `origin:"blocked-review"`, `review_failure_ref`, `review_failure_sha256`, `repair_reason`, and `additional_checks` (an array of the normal check objects; use `[]` if none). Omit `spec_path`: the host copies the original `objective`, `nonGoals`, `workspace`, `criteria`, `policy`, `contextRefs` and checks, increments taskRevision and appends only those checks. It does not reinterpret the outcome or select a repair. The legacy `spec_path` form remains supported but cannot be combined with `additional_checks`; changed immutable fields are a bound pre-reservation draft rejection, never permission to alter the contract. Do **not** mix `failure_receipt_ref`/`failure_receipt_sha256` into `origin:"blocked-review"`; those selectors belong to the default staged-check branch or the explicit conflict branch below. The host binds **all** finished waves/findings, old complete candidate C0 and native writer evidence; an incomplete/unknown review, target journal or changed source is not eligible. Preserve all original checks and add a trusted regression where needed. The new managed mutation writer reconstructs C0 with the host-provided command and submits one **complete B→C1** patch—not just C0→C1 or a duplicate of C0. New staging/checks, fresh independent read-only review resolving every old finding, and a new AcceptanceReceipt are mandatory. An approved-integration repair still needs its own exact target plan and a separate per-plan user confirmation before apply and final target checks. The old Task deadline, closed actual usage and role-spawn ceiling carry over. This is not an automatic retry, report-only rewrite or permission to apply.

### Reconstruction input correction (before execution only)

The existing Task leaf hook receives the host-bound reconstruction command through native launch metadata. Before reconstruction succeeds, nonmatching Bash/source-write inputs are blocked **before the tool executes**, with a native `teams-reconstruction-input` custom entry bound to the session, command digest, exact tool call and input digest. Correct these inputs in the same live writer within the original deadline and budget; do not invent a one-correction ceiling, charge a product/process/report repair, seal BLOCKED merely for this input rejection, or launch another writer. Unknown effects or an admitted command that executes and fails still require stop/reconciliation; its execution cannot be retried by this path.

Reconstruction verification permits only those native pre-tool rejections whose paired call/result, input, session and command bindings all match. An ordinary failed Bash (including exit 128), a model's no-write claim, missing/changed proof, a replayed reconstruction or earlier unclassified mutation remains rejected. The exact successful reconstruction/tree proof, original source scope, lineage, owner, usage, deadline, fresh review and acceptance requirements are unchanged. Existing histories without these proofs retain strict verification; no old run is retroactively relabeled. This is native input admission, not a shell parser, automatic retry loop, new tool or sandbox.

### Known isolated integration conflicts

The host may return `teams-completed-integration-conflict/1` with `disposition:"diagnose-only"`. This means ALL captured input patches passed individual base/scope validation, Git terminated with exit 1 and real unmerged entries in the host-owned rehearsal, and the original source/owner remained intact. It is not an acceptance, semantic diagnosis, target-apply conflict or permission to retry stage. Preserve `integration/failure.json`, native captures and the partial index. Signal/timeout/spawn errors, invalid later lanes, incomplete captures, source/owner drift and ambiguous target effects do **not** get this classification.

New stage/checks and a fresh no-write final reviewer must verify preservation and recovery; only then can a new AcceptanceReceipt permit original Goal/Task readback. Approved-integration still requires a new exact plan, separate user confirmation, apply proof and final target checks. No edits to E0, blind replay, automatic third execution or semantic merge by runtime.

The observer retains known check/conflict failures while an active Goal continues L0 diagnosis. It clears no failure from assistant prose or a Goal-complete claim: a successful public accept must bind a real receipt and ledger-accepted same-Task/owner successor to the exact old failure. Acceptance itself still precedes Goal-X readback and reservation closure. Unknown Task/runtime errors still drain safely; this is not a blanket catch-and-continue.

Failed-check, isolated-conflict, report-only and blocked-review product revision are mutually exclusive **within one Task lineage** and share at most one successor execution. Missing/partial/unknown reviews, signaled/mutating/unknown checks, owner/source drift, exhausted budget, accepted work or target apply still block revision: reconcile and request any necessary authority rather than redispatch. This source implementation has disposable native-format fixture evidence, not separately authorized live-model verification.

A closed FAILED/CANCELLED execution cannot be accepted later merely because someone says its old BLOCKED finding has been resolved: acceptance requires a current `RESULT_READY` execution with passing source-bound review and the required checks. For closed work, only a separately admitted new revision can obtain its own fresh review and AcceptanceReceipt; the old terminal state and review remain unchanged.

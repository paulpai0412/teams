# C3 agent execution, repair and re-audit policy

## Scope and authority

User-approved revision (2026-09-14): distinguish agent mistakes from product/runtime defects; main or Worker may request bounded repair/re-audit after auditor rejection/pause. This replaces the historical blanket no-repair/any-anomaly policy for newly prepared C3 work, not historical records. No new controller, repair API, ledger state, dependency patch or automatic retry is introduced. Existing owner, scope, evidence, budget, deadline and terminal-state gates remain.

`c3-prompt.txt` is the revised L0 input for the existing `TEAMS_E2E_PROMPT_FILE` entrypoint. It is not automatically loaded. Before a future authorized run, prepare a fresh Task spec using `c3-task-objective.txt` for its candidate-only objective: substitute `{{patchPath}}` and `{{patchSha256}}` with the approved absolute patch path and verified hash. Keep Goal creation, identity binding, dispatch and final acceptance instructions only in the L0 prompt, not the Task objective/nonGoals or leaf assignment. These are explicit preparation inputs; the runtime does not rewrite arbitrary or historical objectives. For the permitted one report-only correction use the existing `maxReportRepairs: 1`; keep product repairs/process restarts at zero for this approved-patch verify-only scenario, and retain the approved token/spawn/deadline limits. Do not edit r6's sealed zero-repair contract or reuse it under a contradictory prompt. This documentation does not launch a run or resume a Goal.

A policy allowance is a ceiling, not proof of runtime support or a grant to replay tools. Task Pi currently has a `request_report_repair` schema value but no complete public request/handler flow. Do not fabricate a call or write mailbox commands directly. An authorized leaf can correct its own structured_output submission in the same run using its existing tool; this is not reopening a sealed Task result. Otherwise return the precise unsupported step to the owner. Worker requests use existing supervisor/handoff facilities, not Goal control.

## Agent execution

- **Inputs:** this approved-patch candidate does not need optional role-memory lookup. Do not make an optional lookup a required preparation step or create placeholders. A genuinely required missing input still needs a decision. No memory-loader or role-profile change is made.
- **Candidate checks:** native Git/runtime own patch applicability and path-scope validation; do not duplicate them with a hand-written patch-header parser (`/dev/null` is a valid new-file marker). Feed extracted inline JavaScript to `node --check` on stdin, not a process-substitution filename. These are check corrections, not product changes.
- **Allocations:** maxTaskTokens is the aggregate ceiling, including Worker usage, role allocations and final review; never request the whole ceiling as one leaf quota. Actual-usage admission remains authoritative; a schema-valid budget denial is not automatically cleared or replayed by the observer.
- **Verification responsibility:** candidate roles execute assigned checks and preserve handoff. When L0 owns browser checks, keep those criteria indeterminate. Do not invent a mock DOM to substitute for the designated real browser check. Inconclusive development tooling is not proof of a product defect.
- **Reporting:** validate the complete supplied schema before submission. Required `value.residualRisks` is separate from sibling `acceptanceReport.residualRisks`. An authorized correction fixes only the omitted/invalid report fields using existing evidence, retaining the rejected submission. At most one, within the existing run and all limits. Zero allowance or stricter assignment rules mean request a decision, not silently correct.
- **Failures:** preserve exact errors, establish effects, then classify. Product defects require scoped causal repair; failed verification cannot be assumed harmless. Nonfatal checker diagnostics are interpreted using actual checker semantics. Unknown side effects/native termination, failed safety/budget/deadline gates, source/evidence mismatch and unresolved required evidence stop progression and require owner-safe reconciliation.
- **Input rejection:** the observer correlates the original tool name/call ID with the public Task parameter schemas and uses the same public Pi validator as native execution. Only a proven schema rejection is allowed back to the existing agent loop for corrected arguments within the current budget/deadline. It preserves the error and never edits/truncates IDs or sends replacement calls itself. Schema-valid runtime errors, unknown tools/mismatched events and failed safety gates remain fatal. This replaces the old review-selector-only exception; maxReportRepairs remains report-only, not a tool retry budget.
- **Native retry:** Pi model/summarization retries remain allowed within configured bounds. They do not authorize Task redispatch or tool-effect replay.

## Repair / re-audit procedure

1. Preserve the exact audit rejection, Goal/execution identity, source state, original tool errors and existing receipts. Audit rejection is not itself proof that the product needs changing. User pause/unfocus is not repair authorization.
2. Main or Worker may request repair/re-audit. In the existing report/handoff, identify each objection, evidence, owning layer, proposed correction/counter-evidence, allowed scope and remaining gap. No new report schema is required. An unresolved required decision keeps the candidate blocked; requesting repair is not acceptance.
3. Main resolves classification and authority. For a report problem, correct only the report; for interpretation, present counter-evidence; for a proven product problem, fix its cause only in approved scope. Reuse unchanged valid host/review receipts. A changed source invalidates affected evidence and requires appropriate re-verification/review. Do not rebuild already successful work to erase history.
4. A paused Goal remains paused until the owner explicitly authorizes resume through supported controls. Main may prepare the repair request and evidence while paused; Worker cannot resume/complete Goals. Missing capabilities or a terminal execution are not permission to invent another control path.
5. Once objections are addressed, main submits the supported completion/re-audit request with the new correction/clarification evidence. No unchanged repeated requests, forced completion or auditor bypass. The auditor decides again; completion still needs matching native readback and all required gates. Fresh child review is needed for changed source when required, not automatically for a format correction.
6. Record the new repair/re-audit phase separately. Never overwrite the original failed checks/rejection or reopen an accepted/cancelled execution. Do not label a later repaired outcome as an error-free original C3. Existing repair counts and cumulative usage carry forward; phase/execution changes do not reset them. Exhausted allowance or another unsupported failure returns to the owner rather than starting a new loop.
